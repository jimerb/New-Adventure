# Adventure (1978) — reverse-engineering notes

Everything here was derived by hand from `Adventure (1978).bin` (4096 bytes,
MD5 `157BDDB7192754A45372BE196797F284`). The point of this document is that
**nobody has to disassemble the ROM again**. If you are about to build a
variant, read this file plus `MAPS.md`, and load the four JSON files in `data/`.

| File | What it is |
|---|---|
| `ANALYSIS.md` | This file — rules, systems, feel, and the reasoning behind the tables |
| `MAPS.md` | All 31 rooms as ASCII grids, plus the adjacency table |
| `data/rooms.json` | Room records: exits, colors, and the 40×7 wall grid per room |
| `data/objects.json` | Object records: colors, widths, sprite frame counts/heights |
| `data/layouts.json` | The three built-in starting layouts + the Game 3 randomiser ranges |
| `data/behaviour.json` | Creature chase/flee lists, magnet list, castle/key pairing, variant exits |
| `tools/decode-rom.ps1` | Regenerates all four JSON files. `-Bitmaps` also dumps pixel-exact art |
| `tools/make-maps.ps1` | Regenerates `MAPS.md` from `rooms.json` |

Hex addresses like `$F7A7` refer to locations in the ROM as the 6502 sees it
(the cart is mapped at `$F000–$FFFF`, no bankswitching). They are cited so
claims here can be re-checked, not because the port needs them.

---

## 1. Why this game ports so cleanly

There is essentially no procedural content and no hardware-dependent *logic*.
The world is four data tables and the game loop is about eight behaviours. All
the 2600-specific cleverness lives in the renderer, which you throw away.

The whole game is:

- **31 rooms**, 9 bytes each, at `$FE1B`.
- **19 objects**, 9 bytes each, at `$FF44`.
- **3 starting layouts**, 49 bytes each, plus an 11-entry randomiser table.
- Per-creature **pair lists** that drive all AI.

That is the entire design. Everything below is elaboration.

---

## 2. Coordinate system and screen layout

Get this right first; every number in the data files depends on it.

- The play area is **160 × 96 units**.
- The wall grid is **40 columns × 7 rows**. One cell is **4 units wide × 16
  units tall**. Cells are strongly non-square — corridors are wide and short.
  This is a big part of why the game *reads* the way it does.
- **Y increases upward.** Objects live in `y ∈ $0D…$69` (13…105).
- X for objects runs `$03…$9A`; the player gets slightly more room, `$03…$9F`.
- Screen wrap on exit: leaving the **top** re-enters the next room at `y = $0D`,
  the **bottom** at `y = $69`, the **left** at `x = $9A` (`$9E` for the player),
  the **right** at `x = $03`. Verified at `$F634–$F6A9`.

### Room bitmaps are horizontally symmetric

Each room's wall data is 21 bytes: 7 rows × 3 bytes, giving 20 columns for the
**left half only**. The right half is generated by mirroring. This is a
hardware artifact (the TIA reflected playfield), but it is also the single
strongest visual signature of the game — every room is a Rorschach blot.

Two rooms, `14` and `15`, have reflection **off**, so their left half is
*repeated* rather than mirrored. That asymmetry is deliberate and it is what
makes the black maze disorienting to navigate.

**Design decision for the variant:** if you drop the mirroring you get freedom
but you lose the look. I would keep the 40×7 grid and the 4:16 cell ratio
unconditionally, and treat mirroring as an art-direction choice per room.

### Exit order

Room record bytes +5..+8 are **up, right, down, left**. Confirmed from the
edge-wrap code and cross-checked for reciprocity across every non-maze room.
The mazes are deliberately non-reciprocal — going north then south does not
return you where you started. That is a feature, not corrupt data.

## 3. The map

Full grids and the adjacency table are in `MAPS.md`. Structurally:

| Region | Rooms | Color | Character |
|---|---|---|---|
| Select screen | `00` | `66` | Shows the game-number digit |
| Overworld | `01`–`03`, `0C`–`0E`, `1C`, `1D` | various | Open rooms, one or two wall gaps |
| Blue Labyrinth | `04`–`08` | `86` | The big public maze |
| Catacombs | `09`–`0B` | `08` | Dark — triggers the surround |
| Gold Castle | `11` exterior, `12` keep | `1A` | The win condition room |
| White Castle | `0F` exterior, `17`–`1A` maze | `0C` / `36` | `1A` is the entry room |
| Black Castle | `10` exterior, `1B` hall → `13`–`16` maze | `00` / `08` | Darkest region |
| Credits room | `1E` | `66` | Unreachable by normal exits |

Rooms `$1F` and `$20` exist in the table but are garbage — their graphics
pointers land inside the object table. Ignore them; there are 31 real rooms.

### Two mechanisms that sit outside the exit table

**Game-variant exits.** Any exit byte `>= $80` is an indirection:
`destination = table[$FF32][(exit - $80) + gameNumber]`. Six exits use this,
and they are precisely what turns Game 1 into a small kingdom and Games 2–3
into the full map.

| Exit code | Where | Game 1 | Games 2–3 |
|---|---|---|---|
| `$80` | room `01` down | `10` | `0F` |
| `$83` | room `02` down | `05` | `11` |
| `$86` | room `03` down | `1D` | `0A` |
| `$89` | room `1B` (all four) | `1C` | `16` |
| `$8C` | room `1C` down | `1B` | `0C` |
| `$8F` | room `1D` up | `03` | `0C` |

**Castle gates.** Walking off the *bottom* of a castle interior ejects you to
the exterior at `(x $50, y $2C)` and re-closes the gate behind you
(`$F5FF–$F62E`):

| Castle | Exterior | Interior | Key |
|---|---|---|---|
| Gold | `11` | `12` | gold key |
| White | `0F` | `1A` | white key |
| Black | `10` | `1B` | black key |

The gate itself is an animation counter `0 → $1C`; a 12-entry state→sprite
table makes the portcullis visibly slide. Touching a gate with the matching
key toggles it. The mapping lives in a literal table at `$F9A7`.

## 4. Objects

Every object is `(room, x, y)` plus a state byte. Full records in
`data/objects.json`.

| Code | Object | Color | Notes |
|---|---|---|---|
| `00` | Surround | `0C` | Quad-width black box drawn *around* the player |
| `09`/`12`/`1B` | Portcullis ×3 | room color | Fixed at rooms `11` / `0F` / `10` |
| `24` | Credits text | `CB` | Fixed in room `1E` |
| `2D` | Game number | `C8` | Digit on the select screen; 3 frames |
| `36` | **Rhindle** (red dragon) | `36` | Speed 3 — matches the player |
| `3F` | **Yorgle** (yellow dragon) | `1A` | Speed 2 |
| `48` | **Grundle** (green dragon) | `C8` | Speed 2 |
| `51` | Sword | `06` | |
| `5A` | Bridge | `02` | Quad-width |
| `63` | Gold key | `1A` | Opens room `11` |
| `6C` | White key | `0E` | Opens room `0F` |
| `75` | Black key | `00` | Opens room `10` |
| `7E` | Bat | `00` | 2 frames (wings up / down) |
| `87` | **The Dot** | `08` | 1×1 pixel, grey — the magic-wall object |
| `90` | Chalice | `06` | |
| `99` | Magnet | `06` | |
| `A2` | Null | — | Zero-height sentinel meaning "carrying nothing" |

### The player is not in that table

The man is drawn as the TIA *ball*, with its size taken from each room's
control byte. That is why he is a featureless rectangle with no animation
frames at all, and why player-vs-wall collision is a different code path from
object-vs-wall. **For the variant this is pure freedom** — the protagonist has
no canonical appearance to be faithful to. He is a rectangle because the
hardware had one spare object left.

### Sprite inventory

Shapes and frame counts, for planning your own art. Widths are 8 units (×4 for
the quad-width items); heights are in sprite rows, and one row is one y-unit,
so a 20-row dragon stands about 20% of the 96-unit field height.

| Object | Frames | Heights | Frame meaning |
|---|---|---|---|
| Dragons | 3 unique | 20 / 17 / 22 | upright · slain (lying on its back) · jaws open |
| Bat | 2 | 7 / 11 | wings down · wings spread |
| Portcullis | 12 | 4→16→6 | slides open then shut; a barred lattice pattern |
| Chalice | 1 | 9 | goblet: flared bowl, narrow stem, wide foot |
| Sword | 1 | 5 | horizontal, arrowhead-shaped |
| Magnet | 1 | 8 | horseshoe, opening downward |
| Keys | 1 | 3 | tiny, 3 rows — the smallest carryable |
| Bridge | 1 | 24 | quad-width; thick end-posts, thin twin rails between |
| Surround | 1 | 31 | solid quad-width block |
| Dot | 1 | 1 | one pixel |

Exact bitmaps are recoverable any time with
`pwsh -File tools/decode-rom.ps1 -Bitmaps`. They are deliberately not baked
into `data/` — you are drawing new art, and the original pixels are the one
part of this ROM that is purely expressive rather than mechanical.

### Colour palette (NTSC TIA values, as used)

Rooms: `D8` `C8` green · `E8` blue · `86` blue (Blue Labyrinth) · `08` dark
grey (all dark regions) · `98` `B8` `A8` purple/violet overworld · `0C` light
grey (White Castle) · `00` black (Black Castle) · `1A` gold (Gold Castle and
its keep) · `36` red (White Castle maze, Black Castle hall, room `1D`) · `66`
magenta.

The scheme is worth preserving as *relationships* even if you re-pick the
actual hues: each castle owns a colour, its key matches it, dark regions all
share one value, and the labyrinth is a single flat colour across five rooms so
you cannot tell them apart by looking.

## 5. Behaviour

### One generic AI routine

There is a single chase/flee routine. Each creature has a null-terminated list
of zero-page address pairs. If both members are in the same room, the mover
steps toward the second from the first. **When the creature is the first member
of a pair it chases; when it is the second, it flees.** Nothing else encodes
this. Priority is list order — the first matching pair wins.

| Creature | Speed | Flees | Chases (in priority order) |
|---|---|---|---|
| Rhindle | 3 | sword | player, chalice, white key |
| Yorgle | 2 | sword, **gold key** | player, chalice |
| Grundle | 2 | sword | player, chalice, bridge, magnet, black key |
| Bat | — | — | chalice, sword, bridge, gold key, white key, black key, Rhindle, Yorgle, Grundle, magnet |
| Magnet | — | — | attracts gold/white/black key, sword, bridge, chalice (8 units per step) |

Two consequences worth keeping: the bat will pick up and relocate a **dragon**,
and each dragon guards a different subset, so which dragon is between you and
your goal changes what you should be carrying.

### Dragon state machine

One byte per dragon:

| State | Meaning |
|---|---|
| `0` | Roaming — runs the chase/flee list |
| `1` | Dead — sprite flips to the belly-up pose, stops moving |
| `2` | Has swallowed you — your position is slaved to its mouth (`x+3, y-$0A`) |
| `≥3` | Bite wind-up — counts up to `$FC`, then swallows |

Killing a dragon: touch it while carrying the sword. Sets state `1` and fires
sound 3.

The wind-up **seed** is what the difficulty switches actually control:

| | Game 1 | Games 2–3 |
|---|---|---|
| Difficulty B (easy) | `$D0` (≈44 frames to bite) | `$F0` (≈12 frames) |
| Difficulty A (hard) | `$E8` (≈20 frames) | `$F6` (≈6 frames) |

The other difficulty switch decides whether dragons flee the sword at all
(`$F7FA`). On setting **A** they do flee it; on **B** the sword-flee rule is
filtered out of their pair list entirely and they ignore it — so B is the
harder setting here. Two switches, two genuinely different games. Worth
preserving as explicit options rather than a single "difficulty" slider.

### Player

- Moves **3 units per frame per axis**. Rhindle also moves 3 — you cannot
  outrun him, only out-manoeuvre him. Yorgle and Grundle move 2, so you can.
- Carrying: one item at a time (`$9D` holds its code, `$A2` = nothing). The
  held item keeps a fixed offset from you, captured at the moment of pickup —
  so *how* you grab something determines how it dangles, and that offset is
  what lets you poke a carried sword ahead of you.
- Pickup is by collision. Drop is the fire button, plus a sound.
- There is **no health, no lives, no timer, and no score.** Being eaten is
  not death: you are inside the dragon, still rendered, and if someone kills
  that dragon you walk out. This is the most unusual thing about the design and
  I would fight hard to keep it.

### The surround

Any room whose colour is `08` draws a quad-width black box centred on the
player, hiding everything outside a small radius (`$F9E7`). It is not fog of
war and not a light radius — it is a solid rectangle that occludes the room.
Cheap, and still one of the best-feeling mechanics in the game.

### Win condition

Chalice's room `== $12` (the Gold Castle keep). That is the entire check.
No scoring, no ranking.

### The magic dot and the credits room

At `$F673`: if the mover is the player, `x >= $9F`, the current room is `03`,
**and the dot is no longer in room `15`** (where it starts in all three games),
teleport to room `1E` at `x = $03`. Four comparisons. The dot must be carried
out of its home room, taken to the far right edge of room `03`, and then the
wall stops being a wall.

The dot is also flagged specially in collision handling so it can pass through
walls at all. Room `1E` holds a fixed text object and has no legitimate
inbound exit.

## 6. The three built-in games

`data/layouts.json` has exact positions. Summary:

- **Game 1** — small kingdom. Variant exits collapse the map; the sword starts
  inside the Gold Castle keep, the magnet is in the Black Castle hall, and the
  dragons are slower to bite.
- **Game 2** — the full map, fixed layout. Games 2 and 3 share the same
  starting table.
- **Game 3** — full map, then 11 objects are re-rolled into random rooms
  within per-object ranges: chalice restricted to `13`–`1A`, white key to
  `01`–`16`, black key to `01`–`12`, and most everything else `01`–`1D`. Those
  ranges are the designer's hand on the scale — the chalice is always in a
  maze, and the black key is never deep. Keep the *idea* of bounded
  randomisation even if you re-pick the bounds.

The player's start is not in the layout table at all — it is set by the reset
path (`$F390`) to room `11`, `(x $50, y $20)`, just outside the Gold Castle
gate, in every game. The layout table's first entry is the **dot**, which
starts in room `15` in all three games; the magic-wall trigger tests against
exactly that value.

## 7. What I would carry over vs. rewrite

**Carry over as data:**

- The 31-room graph and the 40×7 wall grids (`data/rooms.json`, `MAPS.md`)
- The three layouts and the Game 3 randomiser bounds
- The chase/flee lists, bat priority, magnet list
- The variant-exit table and the castle/key pairing
- Speeds (3 / 3 / 2 / 2) and the four bite-seed values

**Rewrite freely:**

- All rendering. There is no reason to emulate a 2-scanline kernel.
- All sprite art. Keep the silhouette language — big dragons, tiny keys — but
  the pixels are the original's, not yours.
- The player character, which has no canonical look at all.
- Input: joystick is 4 direction bits plus one button, so arrows + spacebar is
  a direct mapping. The console switches need homes: Reset → start, Select →
  cycle game 1/2/3, and the two difficulty switches → explicit toggles.

**Think hard before changing:**

- **Flicker.** On real hardware only two objects can share a scanline band, so
  the original alternates them across frames. A modern port has no such limit,
  but crowded rooms read very differently once everything is solid. Consider
  making this a toggle rather than silently "fixing" it.
- **Mirrored rooms.** Cheap to abandon, expensive to the identity.
- **Being eaten instead of dying.** The temptation to add lives is strong and
  would gut the game.
- **No text, anywhere.** The original explains nothing. That is the design.

## 8. Provenance note

The tables above are facts about how the ROM behaves, and the JSON in `data/`
is derived measurement. The room bitmaps and the character sprites are the
original's expressive artwork, which is why the pixel data is regenerated on
demand from the ROM rather than committed here. For a new game with new art,
reimplementing the mechanics and topology documented in this file is the
normal path; shipping the original bitmaps is the part that carries risk.
Worth settling before art production starts, since it decides whether the room
grids are reference or assets.
